# 검사 주기(T) 스윕 결과 — mtd.h v1 `period_ms` 확정

**측정일** 2026-11-09 · **환경** Docker `gcc:13`, `aarch64`, linuxkit (Docker Desktop VM)
**코드** `docs/poc/{sweep_target.c, run_sweep.sh}`, 주입기 `shadow_injector.c` 재사용 · 재현: `bash docs/poc/run_sweep.sh`
**조건** `/proc/pid/mem` 외부 변조 80회 @150ms 간격. CPU는 감시 변수 1000개를 4초간 폴링한 **검사 스레드 CPU 시간**.

## 결과
| T(ms) | 탐지율 | ≤200ms | 지연 avg(ms) | 지연 max(ms) | 검사 CPU(%) |
|---|---|---|---|---|---|
| 25 | 80/80 | 80 | 14.2 | 30.3 | 0.21 |
| 50 | 80/80 | 80 | 23.9 | 54.0 | 0.12 |
| 75 | 80/80 | 80 | 29.7 | 80.3 | 0.09 |
| 100 | 80/80 | 80 | 41.6 | 105.0 | 0.06 |

## 해석
- **탐지율·오탐은 T와 무관** — 모든 T에서 80/80 탐지, 오탐 0.
- **최대 지연 ≈ T + ~5ms** (폴링 주기 + 스케줄 지터). 평균 ≈ T/2 + 지터.
- **CPU는 제약이 아니다** — 감시 변수 1000개에도 0.06~0.21%. 실제 목표 규모(10개)면 ~100배 작아 사실상 0. 프로젝트 오버헤드 목표(10변수 CPU +10%)는 큰 여유로 충족.
- 따라서 **T는 지연 목표만으로 정해진다**: 탐지 지연 ≤100ms를 지키려면 **T ≤ 75ms**(T=100은 max 105ms로 초과).

## 결정
**기본 검사 주기 `period_ms` = 50ms** 로 확정.
- max 지연 54ms → 목표 100ms에 2배 마진
- CPU 0.12%(1000변수) → 무시 가능
- `mtd.h`의 `MTD_DEFAULT_PERIOD_MS = 50`과 일치(이제 데이터로 뒷받침)

## 한계
- linuxkit/VM 환경 측정. 실제 하드웨어에서 절대 CPU·지터는 다를 수 있으나, "CPU가 지연보다 훨씬 느슨한 제약"이라는 결론은 바뀌지 않을 것.
- CPU는 변하지 않는 filler 변수(스칼라) 비교 기준. 배열형(해시 비교)·감시 변수 수를 크게 늘린 실측은 T5 자원 측정에서 별도로 한다.
