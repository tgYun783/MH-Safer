## 2. 실행 환경 (모든 실험 공통)
- **컨테이너**: `scripts/dev.sh`의 `mh-safer-dev` 이미지(Ubuntu 24.04, g++ 13), `--cap-add=SYS_PTRACE --security-opt seccomp=unconfined`.
- **빌드**: Release (`-DCMAKE_BUILD_TYPE=Release`), 실험한 커밋 해시를 기록.
- **libmtd 설정**: `period_ms = 50`(기본값), `enable_mprotect = 0`, 규칙 파일 `game/rules.json`.
- **호스트 기록**: OS, CPU 모델·코어 수, Docker 버전, 가상화 여부(Docker for Mac 등). 결과표에 같이 적는다.
- **동시 부하**: 실험 중 다른 무거운 작업을 돌리지 않는다. 같은 실행 안에서 게임·주입기 외 프로세스는 띄우지 않는다. 예외: 정상 플레이 시드 5회는 **동시 실행**한다(11-16 PM 결정, 시간 절약). 동시 실행 수는 `meta.json`의 `concurrent_runs`에 남기고 결과표에 적는다.

## 3. 정상 플레이 실험 (오탐률)
변조 없이 봇만 돌려서 나온 alert는 전부 거짓 양성(FP)이다.

| 항목 | 값 |
|---|---|
| 난이도 | `hard`(16×30, 지뢰 99) — 칸 상태·지뢰 배치가 480바이트로 가장 크다 |
| 시드 | `--seed` 1, 2, 3, 4, 5 (실행 5회) |
| 실행 시간 | 실행마다 `--duration-sec 600` (10분) |
| 봇 속도 | `--speed-ms` = §3.1 보정으로 정한 값 |
| 출력 | 주소 로그(`--addr-log`), alert 로그(JSONL, `docs/interface.md` §2) |

### 3.1 봇 속도 보정 (첫 실행 전에 한 번)
`--speed-ms 0`이면 한 판이 1초 안에 끝나 `timer`가 한 번도 오르지 않는다(`game/README.md`). 그러면 `tick` 구간·`delta_eq` 규칙이 검증되지 않아 오탐률이 실제보다 좋게 나온다.
- 기준: **한 판 길이 중앙값 ≥ 10초**(판마다 `tick`이 10회 이상).
- 방법: `--speed-ms` 25, 50, 100, 200으로 각 60초 실행해 판 수를 세고, 기준을 넘는 가장 작은 값을 고른다.

| `--speed-ms` | 60초 동안 끝난 판 수 | 한 판 평균 길이(근사) |
|---|---|---|
| 25 | 10 | ≈ 6초 |
| 50 | 5 | ≈ 12초 |
| 100 | 3 | ≈ 20초 |
| 200 | 1 | ≈ 38초 (끝난 판 1 + 진행 중 판 22초) |

측정 2026-11-14, 커밋 `7a60a01`(main) 게임, `hard`·`--seed 1`·각 60초 1회, 4개 동시 실행. Docker for Mac(8코어) 위 `mh-safer-dev`. 평균 길이는 60초 ÷ 끝난 판 수로 낸 근사(진행 중 판은 무시, 200만 끝난 판 1개 = 60초 − 진행 중 판 22초)이며 **중앙값은 미측정**(게임이 판 길이를 출력하지 않음).
→ **제안: `--speed-ms 50`** (평균 ≈ 12초로 기준에 가장 가까운 최소값). 판 길이 분포는 S2-06 이후 주소 로그(`state_alloc`~`state_free` 간격)로 다시 확인한다.

### 3.2 실행 명령 (S3-02 통합으로 확정)
```bash
./build/game/minesweeper --bot --difficulty hard --seed 1 \
  --speed-ms 50 --duration-sec 600 \
  --addr-log results/<run>/addr.jsonl --alert-log results/<run>/alerts.jsonl \
  --stats results/<run>/stats.json
```
`stats.json`의 `mtd_end_count`가 오탐률 분모(§7), `alerts`는 alert 총수다. 옵션 설명은 `game/README.md` "libmtd 감시".

## 4. 변조 실험 (탐지율·지연)
정상 플레이(§3과 같은 조건, 시드 1~5)를 돌리는 동안 주입기(`injector/`, S3)가 외부 프로세스에서 변조한다. 주소는 주소 로그(`docs/interface.md` §3.1 주입기 규칙)로만 정한다.

### 4.1 시나리오 3종
| 유형 | 정의 | 기대 탐지 | 탐지율 목표 |
|---|---|---|---|
| **T 타이밍 위반형** | 규칙상 그럴듯한 값을, 합법 구간 **밖**에서 쓴다 (예: 구간 밖 `timer` +1, 입력 없이 칸 하나 열기) | behavior | 포함 (≥ 90%) |
| **V 값 위반형** | 규칙에 어긋나는 값을 쓴다 (예: `timer` = 0, `mines_remaining` = 999, `cells_opened` 부풀리기, `game_state` = 승리, 지뢰 제거) | behavior 또는 prediction | 포함 (≥ 90%) |
| **H 은닉형** | 규칙상 그럴듯한 값을, 정상 변경 **직후**(`tick` 등 구간이 닫힌 직후 수 ms 안)에 쓴다 | 한계 측정 | 제외, `hidden=true` |

변수별 대상(주입기 최소 버전이 정할 수 있게 열어 둔 부분은 S3 주입기 PR에서 채운다):

| 변수 | T | V | H |
|---|---|---|---|
| `timer` | 구간 밖 +1 | 0으로 되돌리기 | `tick` 직후 +1 |
| `mines_remaining` | 구간 밖 ±1 | 999 | `flag` 직후 ±1 |
| `mine_field` | — (모든 변화가 위반) | 지뢰 1개 제거·이동 | — |
| `cell_state` | 입력 없이 닫힌 칸 1개 열기 | 열린 칸 닫기 | `reveal` 직후 이웃 칸 열기 |
| `cells_opened` | 구간 밖 +1 | +100 | `reveal` 직후 +1 |
| `game_state` | — | 바로 승리 | — |

시나리오 라벨(`scenario`)은 `<유형>-<변수>` 형식(예: `T-timer`, `V-mine_field`). `docs/interface.md` §3 예시도 이 형식으로 맞췄다(§7, 11-16).

**주입기 구현 (S3-12, 2026-11-20, 담당 결정 — §7에서 위임)**: 표에서 "—"가 아닌 14칸을 `injector/`가 모두 지원한다(`injector/README.md`).
- **H 타이밍 = 같은 변수 폴링(4종 모두)**: 간격이 지나면 대상 변수를 0.2ms마다 `/proc/<pid>/mem`으로 읽어 값이 바뀌는 순간(= `tick`·`flag`·`reveal` 구간의 정상 변경)을 잡고 곧바로 쓴다. 게임·주소 로그는 바꾸지 않는다. 근거: `timer` 최소 버전(§7)과 같은 방식이라 구현이 하나이고, 구간 시작·끝을 알리는 로그 확장 없이 4변수 모두 정상 변경을 직접 관측한다. 정상 변경을 본 시각부터 쓰기까지의 지연(평균·최대)은 주입기 `--stats`에 남긴다(미측정).
- **`cell_state` T·H의 칸 위치 = 무작위 닫힌 안전 칸**(위 표의 "이웃 칸" 대신): 주소 로그에 보드 폭이 없어 이웃을 알 수 없다. 탐지 규칙(구간 밖 변화 / 요소별 `open_only`)은 칸 위치와 무관하므로 결과에 영향이 없다. 지뢰 칸은 열지 않는다(`mine_field`를 읽어 확인, 배치 전에는 쓰지 않음). 보드가 배열 전체(480칸)를 채운다고 가정한다 — 난이도는 `hard` 하나(§7).

### 4.2 반복 횟수와 간격
- **시나리오×변수 칸마다 변조 100건 이상** (시드 5개 × 20건). 100건이면 1건 놓칠 때 1%p라 90% 목표를 판정할 해상도가 된다.
- **변조 간격 ≥ 500ms**(무작위 0~200ms 지터 추가). 탐지 윈도우 W = 200ms보다 길어서 앞 변조의 alert가 다음 라벨에 매칭되지 않는다.
- 한 실행(10분)에는 한 시나리오 유형만 넣는다. 유형끼리 섞이면 채점 때 어느 변조가 어느 alert를 냈는지 갈라 볼 수 없다.
- 판이 바뀌어 대상이 해제된 뒤 들어간 변조는 채점에서 "stale"로 빠진다(`docs/interface.md` §4). stale 비율이 20%를 넘으면 그 실행은 다시 돌린다(유효 변조 수가 모자라서).

## 5. 채점 (`docs/interface.md` §4 그대로)
- 탐지 윈도우 **W = 200ms**. 같은 `name`의 alert가 `inject_ns ≤ detect_ns ≤ inject_ns + W`에 하나 이상 있으면 TP.
- 탐지율 = TP / (`hidden=false` 라벨 수 − stale), 행위·예측 alert를 나눠서도 집계(`kind`).
- 탐지 지연: TP마다 `detect_ns - inject_ns`. 중앙값·p95·최대를 보고한다. 목표 판정은 **p95**로 한다(§7, 11-16).
- 은닉형은 별도 표로 보고.

채점기 실행:
```bash
python3 scripts/score.py --labels results/<run>/labels.jsonl \
  --alerts results/<run>/alerts.jsonl --addr-log results/<run>/addr.jsonl \
  --stats results/<run>/stats.json --meta results/<run>/meta.json
```
`score.json`을 labels 폴더에 만들고 OR·AND·behavior-only·prediction-only 결합 결과를 같은 입력으로 출력한다. AND는 같은 변수의 behavior/prediction alert를 W 안에서 한 쌍으로 묶으며, 각 alert는 한 쌍에만 쓴다.

## 6. 결과 저장
```
results/<YYYY-MM-DD>_<실험>_<시드>/
  meta.json      커밋 해시, 명령, 환경(§2), speed-ms, 시작·종료 시각
  addr.jsonl     게임 주소 로그
  alerts.jsonl   libmtd alert 로그
  labels.jsonl   주입기 정답 라벨 (§4만)
  score.json     채점 결과 (평가 도구가 생성)
```
- `addr`·`alerts`·`labels`는 **원본 데이터**다. 생성 후 고치지 않는다. 다시 돌리면 새 폴더를 만든다.
- `results/`는 **저장소에 올린다**(11-16 PM 결정). 정상 10분 1회 ≈ 40KB라 작다. 한 실험 묶음이 10MB를 넘으면 그때 다시 정한다. 요약표는 `docs/results/`에 둔다.
- 정상 플레이 수집은 `scripts/collect-normal.sh`(시드별 동시 실행, `meta.json`에 `concurrent_runs` 기록), 요약은 `scripts/summarize_normal.py`.

## 7. 결정 (2026-11-16 PM 결정, 원래 열린 질문)
- [x] **오탐률 분모** → **합법 구간 수(`mtd_end` 호출 수)**. 오탐률 = FP / `mtd_end` 호출 수. 함께 **10분당 FP 건수**(절대값)를 보고한다. 근거: alert 수를 분모로 쓰면 정상 플레이에서 1건만 나와도 100%가 되고, 검사 횟수(변수 × 주기)는 분모가 커서 오탐률이 실제보다 좋아 보인다. 합법 구간은 "정상 변경 기회" 수라 뜻이 분명하다. 채점기(S3-21)가 `mtd_end` 호출 수를 세려면 게임이 구간 수를 남겨야 한다 → S3-02에서 alert 로그와 함께 출력.
- [x] **지연 목표 판정 기준** → **p95**. 중앙값·최대도 함께 보고한다. 근거: 최대값은 스케줄링 지연 한 번에 좌우된다.
- [x] **시나리오 라벨 형식** → **`<유형>-<변수>`**(예: `T-timer`). `docs/interface.md` §3 예시를 이 형식으로 바꿨다.
- [x] **H 은닉형 타이밍** → 최소 버전은 **`timer` 변화 폴링**으로 구간 종료를 추정한다(`/proc/<pid>/mem`으로 `timer`를 읽어 값이 바뀐 직후에 쓴다, `tick` 주기 1초). 게임 수정은 필요 없다. 나머지 변수의 H(`flag`·`reveal` 직후)는 S3-12에서 담당(우진)이 같은 폴링 방식이나 주소 로그 확장 중에서 정한다.
- [x] **정상 플레이 난이도** → **`hard` 하나**. 근거: 배열이 가장 크고(480바이트), 3종을 다 돌리면 실행 시간이 3배라 11-20 첫 채점 일정에 맞지 않는다. 다른 난이도는 S4에서 필요하면 추가한다.
- [x] **봇 속도** → **`--speed-ms 50`**(§3.1). S3-02 후 주소 로그(`state_alloc`~`state_free` 간격)로 다시 확인했다: **판 길이 중앙값 11.1초**(54판, 최소 7.6·최대 13.5초) ≥ 10초 → 50 유지. 측정 2026-11-16, PR #28 브랜치 `s3/integration`, `hard`·`--seed 1`·600초 1회, Docker for Mac 위 `mh-safer-dev`, libmtd 켬(T=50ms).

## 8. 판정 결합 비교 (S3-22)
같은 JSONL 입력에서 OR(둘 중 하나), AND(같은 이름·W 안에 behavior와 prediction 모두), behavior-only, prediction-only를 비교한다. 이는 규칙 기반 채점 비교이며 결합 모델을 실제 탐지 결과로 보정한 것은 아니다.

아래 표는 단위 테스트의 **합성 데이터**(정상 실험 결과가 아님)로 계산해 결합 의미론을 확인한 예다.

| 방식 | TP | FN | FP | 탐지율 |
|---|---:|---:|---:|---:|
| OR | 3 | 0 | 4 | 100% |
| AND | 1 | 2 | 2 | 33.3% |
| behavior-only | 1 | 2 | 3 | 33.3% |
| prediction-only | 3 | 0 | 1 | 100% |

실험 결과가 쌓이면 같은 입력 로그로 다시 비교해야 하며, 위 숫자를 실제 탐지율·오탐률로 인용하지 않는다.
