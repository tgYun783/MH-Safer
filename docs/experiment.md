## 2. 실행 환경 (모든 실험 공통)
- **컨테이너**: `scripts/dev.sh`의 `mh-safer-dev` 이미지(Ubuntu 24.04, g++ 13), `--cap-add=SYS_PTRACE --security-opt seccomp=unconfined`.
- **빌드**: Release (`-DCMAKE_BUILD_TYPE=Release`), 실험한 커밋 해시를 기록.
- **libmtd 설정**: `period_ms = 50`(기본값), `enable_mprotect = 0`, 규칙 파일 `game/rules.json`.
- **호스트 기록**: OS, CPU 모델·코어 수, Docker 버전, 가상화 여부(Docker for Mac 등). 결과표에 같이 적는다.
- **동시 부하**: 실험 중 다른 무거운 작업을 돌리지 않는다. 같은 실행 안에서 게임·주입기 외 프로세스는 띄우지 않는다.

## 3. 정상 플레이 실험 (오탐률)
변조 없이 봇만 돌려서 나온 alert는 전부 거짓 양성(FP)이다.

| 항목 | 값 |
|---|---|
| 난이도 | `hard`(16×30, 지뢰 99) — 칸 상태·지뢰 배치가 480바이트로 가장 크다 |
| 시드 | `--seed` 1, 2, 3, 4, 5 (실행 5회) |
| 실행 시간 | 실행마다 `--duration-sec 600` (10분) |
| 봇 속도 | `--speed-ms` = §3.1 보정으로 정한 값 |
| 출력 | 주소 로그(`--addr-log`), alert 로그(JSONL, `docs/interface.md` §2) |

### 3.1 봇 속도 보정 (첫 실행 전에 한 번)
`--speed-ms 0`이면 한 판이 1초 안에 끝나 `timer`가 한 번도 오르지 않는다(`game/README.md`). 그러면 `tick` 구간·`delta_eq` 규칙이 검증되지 않아 오탐률이 실제보다 좋게 나온다.
- 기준: **한 판 길이 중앙값 ≥ 10초**(판마다 `tick`이 10회 이상).
- 방법: `--speed-ms` 25, 50, 100, 200으로 각 60초 실행해 판 수를 세고, 기준을 넘는 가장 작은 값을 고른다.

| `--speed-ms` | 60초 동안 끝난 판 수 | 한 판 평균 길이(근사) |
|---|---|---|
| 25 | 10 | ≈ 6초 |
| 50 | 5 | ≈ 12초 |
| 100 | 3 | ≈ 20초 |
| 200 | 1 | ≈ 38초 (끝난 판 1 + 진행 중 판 22초) |

측정 2026-11-14, 커밋 `7a60a01`(main) 게임, `hard`·`--seed 1`·각 60초 1회, 4개 동시 실행. Docker for Mac(8코어) 위 `mh-safer-dev`. 평균 길이는 60초 ÷ 끝난 판 수로 낸 근사(진행 중 판은 무시, 200만 끝난 판 1개 = 60초 − 진행 중 판 22초)이며 **중앙값은 미측정**(게임이 판 길이를 출력하지 않음).
→ **제안: `--speed-ms 50`** (평균 ≈ 12초로 기준에 가장 가까운 최소값). 판 길이 분포는 S2-06 이후 주소 로그(`state_alloc`~`state_free` 간격)로 다시 확인한다.

### 3.2 실행 명령 (S2-06 통합 후 확정)
```bash
./build/game/minesweeper --bot --difficulty hard --seed 1 \
  --speed-ms <보정값> --duration-sec 600 \
  --addr-log results/<run>/addr.jsonl --alert-log results/<run>/alerts.jsonl
```
`--alert-log`는 아직 없는 옵션이다(S2-06에서 게임에 붙일 예정, 이름은 통합 PR에서 확정).

## 4. 변조 실험 (탐지율·지연)
정상 플레이(§3과 같은 조건, 시드 1~5)를 돌리는 동안 주입기(`injector/`, S3)가 외부 프로세스에서 변조한다. 주소는 주소 로그(`docs/interface.md` §3.1 주입기 규칙)로만 정한다.

### 4.1 시나리오 3종
| 유형 | 정의 | 기대 탐지 | 탐지율 목표 |
|---|---|---|---|
| **T 타이밍 위반형** | 규칙상 그럴듯한 값을, 합법 구간 **밖**에서 쓴다 (예: 구간 밖 `timer` +1, 입력 없이 칸 하나 열기) | behavior | 포함 (≥ 90%) |
| **V 값 위반형** | 규칙에 어긋나는 값을 쓴다 (예: `timer` = 0, `mines_remaining` = 999, `cells_opened` 부풀리기, `game_state` = 승리, 지뢰 제거) | behavior 또는 prediction | 포함 (≥ 90%) |
| **H 은닉형** | 규칙상 그럴듯한 값을, 정상 변경 **직후**(`tick` 등 구간이 닫힌 직후 수 ms 안)에 쓴다 | 한계 측정 | 제외, `hidden=true` |

변수별 대상(주입기 최소 버전이 정할 수 있게 열어 둔 부분은 S3 주입기 PR에서 채운다):

| 변수 | T | V | H |
|---|---|---|---|
| `timer` | 구간 밖 +1 | 0으로 되돌리기 | `tick` 직후 +1 |
| `mines_remaining` | 구간 밖 ±1 | 999 | `flag` 직후 ±1 |
| `mine_field` | — (모든 변화가 위반) | 지뢰 1개 제거·이동 | — |
| `cell_state` | 입력 없이 닫힌 칸 1개 열기 | 열린 칸 닫기 | `reveal` 직후 이웃 칸 열기 |
| `cells_opened` | 구간 밖 +1 | +100 | `reveal` 직후 +1 |
| `game_state` | — | 바로 승리 | — |

시나리오 라벨(`scenario`)은 `<유형>-<변수>` 형식(예: `T-timer`, `V-mine_field`). `docs/interface.md` §3 예시의 `"S1-immutable"`은 이 형식으로 맞춘다(§7 열린 질문).

### 4.2 반복 횟수와 간격
- **시나리오×변수 칸마다 변조 100건 이상** (시드 5개 × 20건). 100건이면 1건 놓칠 때 1%p라 90% 목표를 판정할 해상도가 된다.
- **변조 간격 ≥ 500ms**(무작위 0~200ms 지터 추가). 탐지 윈도우 W = 200ms보다 길어서 앞 변조의 alert가 다음 라벨에 매칭되지 않는다.
- 한 실행(10분)에는 한 시나리오 유형만 넣는다. 유형끼리 섞이면 채점 때 어느 변조가 어느 alert를 냈는지 갈라 볼 수 없다.
- 판이 바뀌어 대상이 해제된 뒤 들어간 변조는 채점에서 "stale"로 빠진다(`docs/interface.md` §4). stale 비율이 20%를 넘으면 그 실행은 다시 돌린다(유효 변조 수가 모자라서).

## 5. 채점 (`docs/interface.md` §4 그대로)
- 탐지 윈도우 **W = 200ms**. 같은 `name`의 alert가 `inject_ns ≤ detect_ns ≤ inject_ns + W`에 하나 이상 있으면 TP.
- 탐지율 = TP / (`hidden=false` 라벨 수 − stale), 행위·예측 alert를 나눠서도 집계(`kind`).
- 탐지 지연: TP마다 `detect_ns - inject_ns`. 중앙값·p95·최대를 보고한다(목표 판정은 최대가 아니라 p95로 할지 §7에서 정함).
- 은닉형은 별도 표로 보고.

## 6. 결과 저장
```
results/<YYYY-MM-DD>_<실험>_<시드>/
  meta.json      커밋 해시, 명령, 환경(§2), speed-ms, 시작·종료 시각
  addr.jsonl     게임 주소 로그
  alerts.jsonl   libmtd alert 로그
  labels.jsonl   주입기 정답 라벨 (§4만)
  score.json     채점 결과 (평가 도구가 생성)
```
- `addr`·`alerts`·`labels`는 **원본 데이터**다. 생성 후 고치지 않는다. 다시 돌리면 새 폴더를 만든다.
- `results/`를 저장소에 올릴지(용량)는 S3 첫 채점 때 정한다. 올리지 않으면 요약표(`score.json`)만 `docs/`에 옮긴다.
